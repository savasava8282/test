# Roadmap проекта «Погода и магнитные бури»

## Принцип работы

Каждый новый этап начинается только после проверки предыдущего. Один запуск Codex — одна ограниченная техническая задача.

## Этап 0. Обязательные правила

1. Прочитать обязательные правила student-kit.
2. Зафиксировать правила в рабочем контексте текущего диалога.
3. Прочитать `rules.md` проекта.
4. Не начинать технические действия, пока не восстановлен текущий stop-point.

## Этап 1. Стартовая документация

1. Согласовать идею.
2. Провести стартовую разведку рынка и источников данных.
3. Согласовать техническое задание.
4. Создать резервные Markdown-документы:
   - `technical_spec.md`;
   - `roadmap.md`;
   - `rules.md`;
   - `current_status.md`;
   - `module_map.md`;
   - `start_prompt_for_next_chat.md`.
5. Не создавать `next_steps.md`.

## Этап 2. GitHub-репозиторий

1. Уточнить, есть ли у пользователя аккаунт GitHub.
2. Создать или подготовить пустой GitHub-репозиторий.
3. Проверить ссылку и текущее содержимое репозитория.
4. Не начинать разработку приложения.

## Этап 3. Deploy key для Codex

1. Дать Codex отдельную задачу на проверку репозитория.
2. Создать или найти SSH deploy key внутри среды Codex.
3. Private key оставить только внутри среды Codex.
4. Показать пользователю только public key.
5. Добавить public key в GitHub через `Settings → Deploy keys → Add deploy key`.
6. Включить `Allow write access`.
7. Если SSH-порт 22 недоступен, использовать `ssh.github.com` и порт 443.
8. Не использовать GitHub-интеграцию Codex и не создавать GitHub token в базовом процессе.

## Этап 4. Рабочая документация в GitHub

1. Проверить SSH-доступ Codex через deploy key.
2. Настроить SSH remote.
3. Создать в корне репозитория ровно шесть согласованных Markdown-файлов.
4. Не создавать `next_steps.md`.
5. Не создавать код приложения.
6. Проверить список изменений.
7. Сделать commit.
8. Сделать push.
9. Получить commit hash или ссылку на commit.
10. Проверить результат через GitHub.

## Этап 5. Первая техническая основа

1. Получить proof текущего состояния репозитория.
2. Выбрать минимальную структуру Python-проекта.
3. Добавить конфигурацию без секретов.
4. Добавить локальную SQLite-базу и схему настроек.
5. Добавить безопасное чтение переменных окружения.
6. Добавить минимальный запуск приложения.
7. Проверить запуск.
8. Сделать отдельный commit и push.

## Этап 6. Минимальный Telegram-бот

1. Зарегистрировать бота через BotFather с пошаговой инструкцией.
2. Не отправлять токен в ChatGPT или GitHub.
3. Настроить токен только на сервере.
4. Реализовать `/start`, `/help`, `/settings`, `/today` как отдельные небольшие задачи.
5. Проверить ответы в реальном Telegram.
6. Зафиксировать результат в Git.

### Подэтап 6.1. Минимальный слой подключения к Bot API

- Бот зарегистрирован как `@weather_storm_alert_bot`.
- Токен сохранён пользователем вне Git в `/root/.config/weather-alert-bot/env`; права файла проверены как `600`.
- Пользователь отдельно проверил токен методом `getMe`; Telegram подтвердил токен, ID бота `8980247554`, имя `Погода и магнитные бури`.
- В проекте создан минимальный `TelegramClient` на стандартной библиотеке Python с методом `get_me()`.
- Добавлена безопасная команда `--check-telegram` без polling и отправки сообщений.
- Client и команда проверяются mock-тестами без настоящего токена.
- Сам токен Codex не читал и не выводил.
- Commit `dd7edd14732fe08950569bab369ba35828341220` независимо проверен в GitHub; он содержит минимальный Telegram API client и команду `--check-telegram`.
- После проверки commit пользователь выполнил реальный запуск нового кода на сервере во временной подсессии; токен был загружен из `/root/.config/weather-alert-bot/env`.
- Команда завершилась успешно. Telegram вернул: токен принят — да, ID бота `8980247554`, username `@weather_storm_alert_bot`, имя `Погода и магнитные бури`.
- Токен не появился в выводе; подтверждено, что новый код проекта может связаться с Telegram Bot API.
- Реальный запуск не включал polling и отправку сообщений.
- `/start`, polling, погодная логика, база данных, планировщик и рассылки ещё не реализованы.

### Подэтап 6.2. Однократная обработка новой команды `/start`

- Исходная точка задачи — commit `c7bebabfe61bbd5ae193fdb728369d97d0259166`.
- В `TelegramClient` добавлены официальные методы `getUpdates` и `sendMessage`.
- Добавлены неизменяемые модели `TelegramMessage` и `TelegramUpdate`.
- Создан `start_handler.py` для одного контролируемого ответа.
- Перед ожиданием новые запросы без ожидания логически очищают старую очередь продвижением `offset`; старые сообщения не получают ответов.
- Затем обработчик ждёт только новую приватную текстовую `/start` или `/start@weather_storm_alert_bot`.
- Отправляется одно фиксированное приветствие, после успешной отправки процесс завершается.
- `--wait-for-start` добавлен во взаимоисключающую группу с `--check-telegram`.
- Добавлены mock-тесты; настоящий токен Codex не читался.
- Реальный запуск нового обработчика и реальное сообщение в Telegram ещё не выполнялись.

### Текущий stop-point после подэтапа 6.2

Минимальная однократная обработка команды `/start` создана и проверена автоматическими mock-тестами без настоящего токена. Код умеет очистить старые обновления, дождаться новой команды `/start`, отправить одно фиксированное приветствие и завершиться. Реальный запуск с Telegram ещё не выполнялся. Следующий безопасный шаг — после независимой проверки commit выполнить контролируемый ручной тест новой команды `/start` с токеном, загруженным из файла вне Git.

## Этап 7. География и расписание

1. Выбор города текстом.
2. Подтверждение найденного города.
3. Сохранение координат и часового пояса.
4. Изменение времени ежедневной отправки.

6. Включение и отключение ежедневной сводки.
7. Проверка отправки в установленное время.

## Этап 8. Погодная сводка

1. Подключить основной погодный источник.
2. Получить почасовой прогноз.
3. Сформировать температуру, осадки, ветер и порывы.
4. Добавить время обновления данных.
5. Реализовать честную обработку недоступного источника.
6. Проверить `/today`.

## Этап 9. Геомагнитный прогноз

1. Подключить официальные данные NOAA SWPC.
2. Получить прогноз Kp.
3. Отобразить уровень G1–G5.
4. Добавить пользовательский порог.
5. Помечать прогноз на четвёртый-пятый день как предварительный.
6. Проверить защиту от медицинских обещаний.

## Этап 10. Категории предупреждений

Добавлять по одной категории за отдельный проверяемый шаг:

1. Сильная жара.
2. Сильный холод.
3. Сильный дождь.
4. Сильная гроза.
5. Сильный ветер.
6. Шторм.
7. Гололёд и гололедица.
8. Сильная магнитная буря.

Для каждой категории отдельно проверить:

- включение и отключение;
- предварительное предупреждение;
- уведомление о начале;
- существенное обновление;
- завершение;
- отсутствие дублей.
