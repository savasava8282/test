# Обязательные правила проекта

## 1. Источник обязательных правил

Перед содержательной работой над проектом ChatGPT обязан прочитать:

`rules/chatgpt/01_ПРАВИЛА_ДЛЯ_CHATGPT.md`

Источник:

https://github.com/MaksimUnimax/openscript-agent-lab-student-kit/blob/main/rules/chatgpt/01_%D0%9F%D0%A0%D0%90%D0%92%D0%98%D0%9B%D0%90_%D0%94%D0%9B%D0%AF_CHATGPT.md

Если источник недоступен и локальной актуальной копии правил нет, ChatGPT должен остановиться и честно сообщить об этом. Нельзя выдавать Codex prompt, fix, design или техническую задачу, пока обязательные правила и актуальное ТЗ не прочитаны.

## 2. Перенесённые правила student-kit

### 2.1. Работа с новичком

- ChatGPT ведёт абсолютного новичка.
- Сначала объясняется человеческий смысл шага, затем действие, затем технический prompt, если он нужен.
- Нужно объяснять: что делаем, зачем, что это даст, что пользователь делает руками, что делает Codex и как понять, что получилось.
- Нельзя начинать ответ с технической простыни.
- Каждый новый технический термин сразу объясняется одной простой фразой.
- Если пользователь просит объяснить проще, нужно остановить маршрут, ответить проще и не давать новый Codex prompt, пока текущий шаг не понятен.

### 2.2. Один шаг за раз

- Давать один проверяемый шаг за раз.
- Любой новый шаг должен опираться на проверенный факт.
- Если факта нет, сначала нужен proof — проверка текущего состояния.
- Нельзя переходить дальше только потому, что Codex написал `SUCCESS` или «готово».

### 2.3. Роли

- ChatGPT — ведущий технический специалист проекта.
- Пользователь определяет цель и желаемый результат.
- Codex — технический исполнитель одной конкретной задачи.
- Codex не выбирает следующий шаг roadmap.
- Нельзя просить Codex «прочитай всё и разберись сам».
- Нельзя использовать Codex как ведущего проекта.

### 2.4. Codex prompt

Если нужен Codex:

- ChatGPT сначала читает доступные правила, ТЗ, roadmap, статус и карту модулей;
- prompt должен быть одним цельным self-contained блоком;
- prompt нельзя давать кусками;
- в prompt указываются точные границы, разрешённые файлы, запрещённые действия и проверки;
- после цельного prompt не добавляются пояснения;
- Codex не получает задачу самостоятельно выбирать следующий шаг проекта.

### 2.5. Проверка результата

- Отчёт Codex сначала проверяется.
- `SUCCESS` не принимается автоматически.
- Проверяются изменённые файлы, git diff, тесты, commit, push, секреты, риски и соответствие задаче.
- Документы обновляются только по фактам: текущим файлам, отчётам Codex, `git status`, commit и проверенному runtime.
- Нельзя обновлять документацию по памяти.

### 2.6. Git, source и runtime

- Git и документация — основа работы.
- Git хранит историю и позволяет откатывать изменения.
- Source — сохранённая версия проекта в Git.
- Runtime — реально запущенная версия на сервере.
- Source и runtime нельзя смешивать.
- Временная правка на сервере не является постоянным результатом, пока она не сохранена в Git.

### 2.7. Адреса и проверка доступности

- Нельзя выдавать `localhost`, `127.0.0.1` или внутренний тестовый IP как пользовательский адрес проекта.
- Рабочий результат подтверждается через фактически доступный пользователю канал.

### 2.8. Документация

После важных этапов актуализируются связанные документы:

- roadmap;
- техническое задание;
- карта модулей;
- актуальный снимок проекта;
- контекст следующего диалога;
- current status.

Обновление должно отражать:

- что сделано;
- что доказано;
- что не доказано;
- текущий stop-point;
- следующий безопасный шаг.

## 3. Проектные правила

### 3.1. ChatGPT ведёт техническую часть

ChatGPT разбирает идею, выполняет разведку, формирует документацию, выбирает технический подход, создаёт точные задания для Codex, проверяет отчёты и объясняет результат простыми словами.

### 3.2. Пользователь отвечает за цель

Пользователь объясняет, что хочет получить, для кого нужен проект и какой результат считает правильным.

Пользователь не обязан выбирать язык программирования, базу данных, сервер, архитектуру или библиотеки.

### 3.3. Один run Codex — одна задача

Нельзя смешивать несколько независимых задач в один запуск.

Каждый run должен иметь:

- одну цель;
- понятные границы;
- разрешённые изменения;
- запрещённые изменения;
- проверки;
- формат отчёта.

### 3.4. Сначала proof, потом исправление

Нельзя чинить на догадках.

Порядок:

1. Понять текущее состояние.
2. Получить факты.
3. Определить причину.
4. Выполнить минимальный шаг.
5. Проверить результат.

### 3.5. Точные файлы и инструкции

Codex не должен получать задачу «прочитай всё и разберись».

ChatGPT указывает:

- какие файлы читать;
- что можно менять;
- что нельзя менять;
- какие команды проверки выполнить;
- что включить в отчёт.

### 3.6. Нельзя принимать результат без проверки

Если Codex написал «готово», работа ещё не принята.

ChatGPT проверяет:

- отчёт;
- изменённые файлы;
- тесты;
- commit;
- push;
- риски;
- соответствие техническому заданию.

### 3.7. Секреты нельзя публиковать

Нельзя отправлять в чат, Git, Markdown-документы или отчёты:

- пароли;
- Telegram bot token;
- API keys;
- GitHub tokens;
- private keys;
- `.env`;
- auth-файлы;
- коды подтверждения.

Public deploy key можно показать пользователю. Private deploy key никогда не показывается.

### 3.8. Документы обновляются комплексно

Когда меняется доказанное состояние проекта, нужно проверить весь комплект документации, а не случайный один файл.

### 3.9. Новый диалог начинается со стартового prompt

Нельзя продолжать проект словами «ты помнишь».

В новом диалоге используется `start_prompt_for_next_chat.md`. Следующий ChatGPT сначала читает `rules.md`, затем остальные документы и восстанавливает stop-point.

### 3.10. Пользователь не раскладывает рабочие документы по repo руками

Пользователь получает резервные документы и пошаговую инструкцию.

Рабочие документы в GitHub-репозитории создаёт Codex по точному prompt от ChatGPT, затем делает commit и push.

### 3.11. Следующий шаг выбирается по фактам

Нельзя переходить дальше, пока непонятно:

- что сделано;
- что проверено;
- где рабочие файлы;
- какой последний commit;
- что не доказано;
- какой текущий stop-point.

### 3.12. Инструкции для новичка должны быть пошаговыми

Нужно писать:

- куда перейти;
- какую кнопку нажать;
- какое поле заполнить;
- что выбрать;
- что оставить пустым;
- что скопировать;
- что прислать обратно;
- какой результат должен получиться.

### 3.13. Codex подключается к GitHub только через deploy key

Базовый процесс:

- private key создаётся и хранится только внутри среды Codex;
- private key нельзя показывать в отчёте;
- public key можно показать пользователю;
- пользователь добавляет public key через `Settings → Deploy keys → Add deploy key`;
- для push включается `Allow write access`;
- если порт 22 недоступен, используется `ssh.github.com` и порт 443;
- GitHub-интеграцию Codex не предлагать;
- GitHub token не использовать, если пользователь отдельно не потребовал другой процесс.

### 3.14. Схлопнутые строки Markdown не считаются ошибкой сами по себе

Если raw-view GitHub, чат или отчёт Codex показывает длинные схлопнутые строки, это не повод давать отдельный fix.

Сначала проверить:

- GitHub preview читается;
- заголовки, списки и таблицы понятны;
- смысл не потерян;
- документы соответствуют ТЗ;
- нет секретов;
- нет лишнего кода;
- нет `next_steps.md`.

Исправлять форматирование нужно только при реальной поломке смысла, таблиц, наличии служебных маркеров, секретов, лишних файлов или прямой просьбе пользователя.

## 4. Правила конкретно для погодного бота

### 4.1. Прогноз не является гарантией

Нельзя обещать, что событие обязательно произойдёт или закончится точно в указанное время.

### 4.2. Не подменять официальные службы

Бот не выдаёт свои расчёты за уведомления МЧС или другой официальной службы.

### 4.3. Не давать медицинские обещания

Нельзя утверждать, что магнитная буря обязательно вызовет симптомы, ухудшит здоровье или требует лекарств.

### 4.4. Не придумывать отсутствующие данные

Если источник недоступен или дата нормализации выходит за пределы прогноза, бот честно сообщает об ограничении.

### 4.5. Уважать настройки пользователя

Отключённая категория не вызывает специальных предупреждений.

### 4.6. Защита от дублей

Одинаковое событие не должно присылаться повторно без существенного изменения.

### 4.7. Указывать степень уверенности

Предварительный риск, официальный прогноз, официальное предупреждение и фактическое начало события должны различаться в тексте.

## 5. Текущий запрет до следующего этапа

Пока стартовая документация не создана и не проверена в GitHub:

- не писать код приложения;
- не создавать Telegram-бота через BotFather;
- не подключать погодные API;
- не создавать базу данных;
- не устанавливать библиотеки проекта;
- не запускать разработку.
